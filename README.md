# AI Ticket 智能工单管理与自动化系统

客户提交问题 → 真实模型分析并按需查询模拟订单 → 按类别自动分派 → 高优先级工单发送飞书通知 → 管理员处理 → 客户凭编号与邮箱查看进度。

## 1. 快速开始

```bash
# 1. 准备环境变量
cp .env.example .env
# 编辑 .env，填入 MODEL_API_KEY

# 2. 一键启动（网页 + 后端 + 模拟通知服务）
docker compose up --build
```

访问地址：

| 端 | 地址 |
| --- | --- |
| 用户端 | http://localhost:8080/ |
| 管理端 | http://localhost:8080/admin |
| 后端 API | http://localhost:8000/api/health |
| Mock 飞书 | http://localhost:9000/messages |

停止与重启（保留数据）：

```bash
docker compose down      # 不要加 -v
docker compose up        # 数据仍在
```

## 2. 模型配置

后端通过 OpenAI 兼容协议调用真实模型，只认三个环境变量，密钥只存在于后端环境变量中，不进入前端与源码。

```env
MODEL_BASE_URL=https://open.bigmodel.cn/api/paas/v4
MODEL_API_KEY=你的智谱 API Key
MODEL_NAME=glm-4.5-flash
```

本次开发与验收使用的服务：**智谱 BigModel（OpenAI 兼容协议）**，模型 **glm-4.5-flash**（免费额度即可调用）。如需更强推理可换成 `glm-5.3-flash` / `glm-4.6`，账号需有对应余额或资源包。
如需换用 DeepSeek / Ollama / 其他兼容服务，只改这三项即可，无需改代码。

- 未配置 Key 或模型不可达时：工单仍会保存，管理端显示“分析失败”，恢复后点击“重新分析”即可。
- 模型密钥不会出现在任何前端代码、镜像或仓库文件中；`.env` 已加入 `.gitignore`。
- 提交 ZIP 或推送仓库前请确认不包含 `.env`，只提交 `.env.example`。

## 3. 功能说明

### 用户端

- 提交姓名、邮箱、问题描述；订单号可单独填写，也可直接写在描述里（自动识别 `A1001` 这类订单号）。
- 提交后生成唯一工单号（`TK-日期-随机码`），提交按钮在请求完成前锁定，并使用提交令牌保证网络重试不会重复建单；内容相同的新一次提交仍会正常建新工单。
- 查询必须“工单编号 + 提交邮箱”同时正确，邮箱不匹配时统一返回查不到。
- 用户只能看到处理状态与管理员公开回复，AI 分析、优先级、内部建议不展示。

### 管理端

- 查看原始问题、AI 类别 / 优先级 / 摘要 / 建议、负责人、工具调用记录、通知结果。
- 可修改负责人、状态（待处理 / 处理中 / 已解决）、填写公开回复、重新分析任意工单、重试失败或结果未知的通知。
- 所有修改写入 SQLite，刷新页面与容器重启后仍然保留。

### 分配规则

| AI 类别 | 部门 | 负责人 |
| --- | --- | --- |
| 技术问题 | 技术组 | 陈工 |
| 支付与退款 | 售后组 | 李静 |
| 其他 | 客服组 | 王琳 |

### 工具调用

模型根据问题自行决定是否调用只读工具：

- `query_order(order_id)`：查询订单状态
- `query_payment(order_id)`：查询支付记录

模拟数据在 `backend/app/mock_data.py` 中预置：

| 订单号 | 订单状态 | 支付记录 |
| --- | --- | --- |
| A1001 | 已发货 | 1 笔成功支付 ¥199 |
| A1002 | 待发货 | 2 笔成功支付，各 ¥299 |
| 其他（如 A9999） | 不存在 | 返回“订单不存在” |

工具名、入参、返回结果都会落库，管理端按时间线展示，作为 AI 建议的事实依据。

### 通知规则与状态机

只有高优先级工单发送通知，内容包含：工单编号、问题摘要、优先级、部门、负责人。

```
分析成功且优先级=高
  且该工单从未有过通知记录
        ↓
    sending（原子抢占，防并发双发）
        ↓ 后端超时 10 秒
 2xx + code=0 → success   （永久终止，任何重试都跳过）
 4xx / 5xx    → failed    （管理端可重试）
 超时 / 连接结果不明 → unknown（显示“结果未知”，不自动重发，仅管理员手动确认后重试）
```

- 已成功的通知绝不重复发送：重新分析即使仍为高优先级也不会再次发送。
- 超时不算成功、不算失败，管理端显示“结果未知”。
- 后端发送超时时间由 `NOTIFY_TIMEOUT_SECONDS` 控制，默认 10 秒，不超过题目要求。

## 4. Mock 飞书服务

Mock 是独立容器服务，对宿主机暴露 `9000` 端口，接口与题目约定一致：

| 接口 | 说明 |
| --- | --- |
| `POST /webhook` | 接收 `{"msg_type":"text","content":{"text":"..."}}`，成功返回 `{"code":0,"msg":"success"}` |
| `GET /messages` | 返回已收到的消息（含接收时间与内容） |
| `POST /mode` | `{"mode":"ok"}` 正常；`{"mode":"fail"}` 返回 HTTP 500 不保存；`{"mode":"timeout"}` 先保存再延迟 30 秒返回 |

常用验收命令（Windows PowerShell 使用 `curl.exe`）：

```bash
curl.exe http://localhost:9000/messages

curl.exe -X POST http://localhost:9000/mode -H "Content-Type: application/json" -d "{\"mode\":\"fail\"}"
curl.exe -X POST http://localhost:9000/mode -H "Content-Type: application/json" -d "{\"mode\":\"ok\"}"
curl.exe -X POST http://localhost:9000/mode -H "Content-Type: application/json" -d "{\"mode\":\"timeout\"}"
```

把 `.env` 中的 `FEISHU_WEBHOOK_URL` 换成真实飞书群机器人地址即可真实发送，无需改代码。

## 验收结果（2026-11-26 实测）

使用智谱 `glm-4.5-flash` 真实模型、Docker Compose 全栈运行，按题目顺序实测：

| 场景 | 实测结果 |
| --- | --- |
| 1 普通咨询 | 类别“其他”、低优先级、客服组；未调用工具、无通知；建议未编造价格 |
| 2 重复扣款 | A1002：调用 `query_payment` 识别 2 笔成功支付，售后组、高优先级，Mock 恰好新增 1 条；A1001：仅 1 笔，中优先级，无通知 |
| 3 模型断线 | 工单保存、分析失败并显示 `Connection error`；恢复地址并重启后重新分析成功，调用 `query_order`，客服组、中优先级，无通知 |
| 4 通知异常 | 重新分析不重发；fail 模式记录失败且 Mock 不新增；切回 ok 后重试成功 +1；timeout 模式显示“结果未知”、Mock +1 且之后不自动重发 |
| 5 重启持久化 | `docker compose down` 后 `up`（未加 `-v`），工单、状态、公开回复与通知记录全部保留，用户凭编号 + 邮箱可查到最新结果 |

自动化测试在容器内同样通过：`docker compose exec api python -m pytest -q` → `10 passed`。

如需清空演示数据重新录制：`docker compose down`，删除 `./data/tickets.db*`，再 `docker compose up -d`。

覆盖内容：

1. 建单幂等（同令牌不重复建单、内容相同的新提交正常建单）、查询鉴权（错误邮箱查不到）、用户端不泄露 AI 字段
2. 低优先级咨询：分到客服组、优先级低、不发送通知
3. 订单 A1002 重复扣款：调用 `query_payment`、识别两笔支付、售后组、高优先级、恰好发送 1 条；重新分析后不重复发送
4. 订单 A1001 仅 1 笔支付：不判为高优先级、不发送通知
5. 工具已核实两笔成功支付但模型误判为中：按题目规则校正为高优先级
6. 通知失败：记录失败原因，切换正常后手动重试成功（新增 1 条），成功后禁止再次重试
7. 通知超时：记录“结果未知”，不自动重发，Mock 侧确实收到 1 条
8. 模型不可达：工单保留、分析失败可查看；恢复后重新分析成功并调用工具
9. 低优先级工单重新分析后变为高优先级：自动补发一次通知
10. Mock 订单目录：A1001 已发货且 1 笔支付、A1002 有 2 笔支付、A9999 返回订单不存在

测试中的模型通过注入的假模型响应驱动，用于稳定验证流程；生产运行时完全使用真实模型，不存在任何写死的分析结果。

## 7. 数据与持久化

SQLite 文件位于宿主机 `./data/tickets.db`，通过 compose volume 挂载到容器 `/app/data`。执行 `docker compose down`（不加 `-v`）后再 `up`，工单、分析、工具调用、通知记录均保留。

- `tickets`：工单主体、状态、部门负责人、公开回复、当前分析、提交令牌
- `analyses`：每次分析的结果或失败原因、模型、耗时
- `tool_calls`：工具名、入参、返回结果
- `notifications`：每次通知尝试的状态、HTTP 码、错误、请求体

## 9. 设计取舍

- **通知不自动重发**：重新分析后即使仍为高优先级，只要工单已有通知记录就不再自动发送，避免触犯“已成功通知不能重复发送”的红线；失败或未知由管理员手动重试。
- **提交幂等**：前端按钮锁定 + 后端提交令牌唯一索引，双保险；不按内容去重，符合“内容相同的新提交仍应正常建单”。
- **分析异步**：提交立即返回工单号，分析在后台执行，管理端轮询刷新；模型慢或断线不会阻塞建单。
- **失败可恢复**：分析失败写独立记录，工单本身不受影响；容器重启会把中断的“分析中”标记为失败，允许重新分析。
- **证据一致性校正**：分类、优先级全部由模型生成；仅当工具真实返回同一订单 ≥2 笔成功支付、而模型仍判为中时，按题目优先级规则校正为高，不生成任何虚构内容，也不替代模型编写摘要与建议。
